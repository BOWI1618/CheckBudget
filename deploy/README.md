# Развёртывание CheckBudget

Ubuntu/Debian, 2 ГБ памяти, PostgreSQL рядом, nginx впереди, TLS от
Let's Encrypt. Всё по шагам; команды выполняются на сервере от root.

Домен ниже обозначен как `budget.example.com` — подставьте свой.

---

## 0. DNS

До всего остального: в панели регистратора создайте **A-запись** на IP
сервера (и `AAAA`, если у сервера есть IPv6).

Проверьте, что запись разошлась, — без этого certbot не выпустит сертификат:

```
dig +short budget.example.com
```

Должен вернуться IP вашего сервера. Обычно это занимает от минуты до часа.

## 1. Код и первичная настройка

```
sudo apt-get update && sudo apt-get install -y git
sudo git clone https://github.com/BOWI1618/CheckBudget.git /opt/checkbudget
sudo /opt/checkbudget/deploy/bin/provision.sh budget.example.com
```

Что делает `provision.sh`:

- ставит nginx, PostgreSQL, certbot и **Node 22** (не «посвежее», а именно
  22.5+: приложение импортирует встроенный `node:sqlite`, которого в 20-й
  ветке нет, и падает на старте);
- заводит системного пользователя `checkbudget` без оболочки;
- создаёт базу и три роли — владельца схемы, роль приложения и роль
  рассылки событий — со **сгенерированными** паролями;
- применяет схему и права;
- пишет `/etc/checkbudget/checkbudget.env` (root:checkbudget, 0640);
- ставит юниты systemd и ночной бэкап.

Скрипт идемпотентен, но при повторном запуске **не перегенерирует**
секреты, если файл окружения уже есть: новый `JWT_SECRET` разлогинил бы
всех, а новый пароль базы просто оборвал бы приложению доступ.

### Почему ролей три

`checkbudget_app` намеренно **не владеет** таблицами. Владелец обходит RLS
везде, где не включён `FORCE`, и второй рубеж защиты исчез бы молча — без
единой ошибки в логах. Пароль владельца схемы лежит отдельно, в
`/etc/checkbudget/owner.env` (root, 0600), и приложению не виден.

## 2. Сертификат

```
sudo certbot --nginx -d budget.example.com
```

**`NXDOMAIN` в ответе certbot** означает, что имени нет в DNS вовсе — не то
что оно указывает не туда. Причины по частоте: A-запись ещё не создана,
создана меньше 10 минут назад (отрицательные ответы кешируются по TTL
из SOA — обычно 600 секунд), или у домена стоят парковочные NS-серверы
регистратора и правки вносятся не в ту зону.

Проверьте снаружи и сравните с адресом самого сервера:

```
dig +short A budget.example.com
curl -s https://api.ipify.org; echo
```

Два адреса должны совпасть. Если первый пуст — записи нет; если он
отличается — запись указывает на парковку регистратора, а не на сервер.

**Вторая по частоте причина — закрытый 80-й порт.** Проверка HTTP-01
ходит на него снаружи, и «сервер пингуется» тут ничего не значит: ICMP
и TCP режутся разными правилами.

Проверьте изнутри — слушает ли nginx и что говорит firewall:

```
sudo ss -lntp | grep -E ':(80|443) '
sudo systemctl status nginx --no-pager
sudo ufw status verbose
```

Если ufw включён, а правила нет:

```
sudo ufw allow 'Nginx Full'
```

Если ufw выключен, а порт всё равно недоступен снаружи — режет firewall
провайдера, и открывать надо в его панели, с сервера туда не дотянуться.
Проверить снаружи можно так (с любой другой машины):

```
curl -sS -m 8 -o /dev/null -w '%{http_code}\n' http://<IP сервера>/
```

Certbot берёт готовый server-блок, копирует его содержимое в новый блок
с TLS и дописывает редирект с 80-го порта. Поэтому в репозитории лежит
**только HTTP-конфиг**: все location-блоки должны существовать до выпуска
сертификата, иначе в HTTPS-версию они не попадут. После certbot файл
изменён им, и `provision.sh` его больше не перезаписывает.

Автопродление certbot настраивает сам — проверить можно так:

```
sudo systemctl list-timers | grep certbot
```

## 3. Первый выкат

```
sudo /opt/checkbudget/deploy/bin/release.sh
```

Скрипт забирает `origin/main`, ставит зависимости, **прогоняет типы и
тесты**, собирает клиент и сервер, применяет недостающие миграции схемы
от имени владельца и перезапускает службу. В конце он не просто смотрит,
что процесс жив, а дожидается ответа от `/health`: упавшее подключение
к базе оставило бы процесс живым и бесполезным.

## 4. Проверка

```
curl -s https://budget.example.com/health
systemctl status checkbudget
journalctl -u checkbudget -f
```

`/health` должен вернуть `{"ok":true,...}` с состоянием пула соединений.

Откройте `https://budget.example.com` — должен появиться экран входа.
Зарегистрируйтесь; первый бюджет создаётся сам.

## 5. Бэкапы

Таймер уже включён и срабатывает в 04:20 с разбросом до 5 минут.
Проверить вручную:

```
sudo /usr/local/bin/checkbudget-backup
ls -la /var/backups/checkbudget
```

**Почему бэкап выполняется от `postgres`, а не от владельца схемы.**
На таблицах включён `FORCE ROW LEVEL SECURITY`, и он действует и на
владельца тоже. `pg_dump` от `checkbudget_owner` отработал бы без единой
ошибки и выгрузил **пустые таблицы**: файл нужного вида, примерно нужного
размера и без данных. Обнаруживается такое ровно в тот день, когда бэкап
понадобился. Суперпользователь RLS не подчиняется — поэтому `postgres`.

Скрипт дополнительно **сверяет себя**: считает операции в базе до выгрузки
и строки в самой выгрузке, и падает с ошибкой, если в базе данные есть,
а в файле нет.

Проверка восстановления (делайте её хотя бы раз — непроверенный бэкап
бэкапом не является):

```
sudo -u postgres createdb checkbudget_restore_test
gunzip -c /var/backups/checkbudget/checkbudget-*.sql.gz \
  | sudo -u postgres psql -q -d checkbudget_restore_test
sudo -u postgres psql -tAc 'SELECT count(*) FROM transactions' -d checkbudget_restore_test
sudo -u postgres dropdb checkbudget_restore_test
```

## 6. Обновление

```
sudo /opt/checkbudget/deploy/bin/release.sh
```

Откат — на предыдущий коммит и тем же скриптом:

```
cd /opt/checkbudget && sudo git reset --hard <хеш> && sudo systemctl restart checkbudget
```

Откат кода **не откатывает схему**. Если в релизе была миграция, сначала
восстановите базу из бэкапа.

## 7. Если что-то пошло не так

**Служба не поднимается.** `journalctl -u checkbudget -n 50`. Частые
причины: не задан `JWT_SECRET` (в production он обязателен, приложение
падает намеренно), неверный пароль в `DATABASE_URL`, не применена схема.

**Пустая страница, в консоли 404 на файлы из `/assets/`.** Браузер держит
старый `index.html`. Так быть не должно: nginx отдаёт его с `no-store`,
и `sw.js` тоже. Проверьте, что конфиг nginx свежий — `nginx -T | grep -A2 'sw.js'`.

**Синхронизация не работает, в консоли ошибка WebSocket.** Проверьте, что
в конфиге nginx есть блок `location /ws` с заголовками `Upgrade` и
`Connection`. Без них апгрейд не проходит, и клиент бесконечно
переподключается.

**Выкидывает при каждом открытии.** Refresh-токен лежит в cookie с
`SameSite=strict` и `Secure`. По HTTP она не ставится вовсе — значит,
сайт открыт не по HTTPS.

**Память.** Служба ограничена 512 МБ. Если она перезапускается по OOM,
это утечка, а не нагрузка: на демонстрационных объёмах Node держится
в пределах 80 МБ. `systemctl status checkbudget` покажет причину.
