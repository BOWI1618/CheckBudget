# CheckBudget — архитектура

Приложение для учёта личного и семейного бюджета: мультивалютное, многопользовательское,
с realtime-синхронизацией между устройствами и устойчивостью к потере связи.

---

## 1. Анализ требований

### 1.1 Что на самом деле определяет архитектуру

Из всего списка требований только четыре реально диктуют технические решения.
Остальное — следствия.

| Требование | Следствие для архитектуры |
|---|---|
| Корректность денег | Целые числа в минорных единицах, никаких `float`. Валюта — часть значения, а не настройка отображения. Курс замораживается в момент записи. |
| Одновременное редактирование | Сервер — единственный источник истины. Оптимистичные блокировки (`version`), явные конфликты, никакой «тихой» перезаписи. |
| Realtime без polling | Журнал событий с монотонным `seq` + WebSocket. Переподключение = догрузка «хвоста», а не полная перезагрузка. |
| Общий бюджет | Авторизация на сервере/БД по членству в бюджете. Ни один запрос не доверяет `budget_id` из тела. |

### 1.2 Явные не-цели MVP

Сознательно вынесено за рамки, чтобы не размывать продукт:

- банковские интеграции и импорт выписок;
- OCR чеков;
- регулярные/повторяющиеся операции (заложено в модели — `transactions.recurrence_id` зарезервирован, но UI нет);
- полноценный CRDT-редактор текстовых заметок;
- нативные приложения (PWA закрывает потребность).

### 1.3 Ключевые ограничения предметной области

1. **Финансовая операция — это факт, а не документ.** Она уже произошла. Значит,
   её нельзя пересчитывать задним числом при изменении курса.
2. **Конфликты редактирования редки, но дороги.** Два человека одновременно
   правят одну операцию — редкость. Но потеря 1500 ₽ из-за «последний победил» —
   это потеря доверия к приложению целиком. Поэтому pessimistic-подход не нужен,
   а вот явное разрешение конфликта — обязательно.
3. **Добавление расхода — 90% использования.** Всё остальное — 10%.
   UX оптимизируется под этот сценарий, даже в ущерб «красоте» остальных экранов.

## 2. Технологический стек

### 2.1 Итоговый выбор

| Слой | Технология |
|---|---|
| Frontend | React 19 + TypeScript + Vite, PWA (Service Worker + Web App Manifest) |
| Состояние | Собственный store поверх нормализованного кеша + IndexedDB (offline) |
| Графики | Собственные SVG-компоненты (без библиотек) |
| Backend | Node.js 22 + Fastify + TypeScript |
| Валидация | Zod — одна схема на границе API, типы выводятся из неё |
| БД (MVP) | SQLite (WAL) через встроенный `node:sqlite` |
| БД (прод) | PostgreSQL 16 — DDL и RLS-политики в `db/postgres/` |
| Realtime | WebSocket (`ws`) + журнал событий с монотонным `seq` |
| Auth | Собственная: scrypt + JWT access (15 мин) + refresh-token rotation в httpOnly cookie |

### 2.2 Почему не Supabase / Firebase

Supabase — самый очевидный кандидат: Postgres + RLS + Realtime + Auth «из коробки».
Он был рассмотрен всерьёз и отклонён по трём конкретным причинам:

1. **Деньги требуют серверной транзакционной логики.** Создание операции — это не
   `INSERT`. Это: резолв курса на дату операции → конвертация в базовую валюту
   целочисленной арифметикой → проверка принадлежности счёта и категории этому
   бюджету → запись операции → запись события в журнал. Всё в одной транзакции.
   В Supabase это уезжает в PL/pgSQL или Edge Functions, то есть бизнес-логика
   расщепляется между двумя языками и двумя местами. Хуже для сопровождения.

2. **Supabase Realtime транслирует изменения строк, а не доменные события.**
   Клиент получает «в таблице `transactions` изменилась строка X». Чтобы построить
   корректный UI, ему всё равно нужен контекст: кто изменил, какая версия, был ли
   это конфликт. И главное — при переподключении Postgres Changes не даёт
   гарантированного «доиграй с позиции N». Приходится делать полную перезагрузку
   данных. Собственный журнал событий с `seq` решает это на порядок чище.

3. **Vendor lock-in на самом чувствительном слое.** Auth + БД + realtime у одного
   провайдера означает, что миграция позже — это переписывание трёх слоёв сразу.

**Firebase/Firestore отклонён жёстче:** документная модель без транзакционных
JOIN-ов плохо ложится на финансовую отчётность (агрегации по категориям за период),
а отсутствие `DECIMAL`/целочисленных гарантий на клиенте (всё в JS `number`)
противоречит требованию №1.

**Когда Supabase был бы правильным выбором:** если бы приложение было
CRUD-ориентированным без сложных инвариантов, или если бы команда была из одного
фронтендера. Здесь — нет.

### 2.3 Почему SQLite в MVP и Postgres в проде

Модель данных, SQL-запросы и вся бизнес-логика написаны в переносимом подмножестве.
Различия изолированы в одном слое (`server/src/db/`).

| | SQLite (MVP) | PostgreSQL (прод) |
|---|---|---|
| Запуск | Ноль зависимостей, файл на диске | Отдельный сервис |
| Конкурентность | WAL, один писатель | MVCC, много писателей |
| Масштабирование | Один процесс | Реплики, пул соединений |
| RLS | Нет — авторизация только в приложении | Есть — второй рубеж защиты |
| Fan-out событий | Прямой broadcast в процессе | `LISTEN/NOTIFY` или Redis pub/sub |

Переезд — это замена драйвера и включение RLS, а не переписывание приложения.
Порог перехода: >1 инстанса сервера или >50 одновременных пишущих пользователей.

## 3. Модель данных

### 3.1 Деньги

**Правило:** денежная величина — это всегда пара `(целое в минорных единицах, код валюты)`.
`float`/`double` не используется нигде, включая транспорт JSON.

```
2500,00 ₽  ->  { amount_minor: 250000, currency: "RUB" }   // exponent(RUB) = 2
1000 ¥     ->  { amount_minor: 100000, currency: "CNY" }
500 JPY    ->  { amount_minor: 500,    currency: "JPY" }   // exponent(JPY) = 0
```

Верхняя граница суммы одной операции — 10^15 минорных единиц. Это гарантирует,
что значение помещается в `Number.MAX_SAFE_INTEGER` (9.007×10^15) и на клиенте
не нужен BigInt для отображения. Вся арифметика конвертации при этом всё равно
выполняется в `BigInt`.

### 3.2 Курсы валют — рациональные числа

Курс хранится как дробь `rate_num / rate_den`, а не как число с плавающей точкой:

```
USD -> RUB = 92,4567   ->  rate_num = 924567, rate_den = 10000
```

Конвертация (целочисленная, без потери точности до финального округления):

```
                amount_minor × rate_num × 10^exp(base)
base_minor = round( ─────────────────────────────────────── )
                       rate_den × 10^exp(source)
```

Округление — half-up, выполняется ровно один раз, в самом конце, в `BigInt`.

### 3.3 Неизменяемость истории

Каждая операция хранит **и** исходные данные, **и** замороженный результат конвертации:

| Поле | Смысл |
|---|---|
| `amount_minor`, `currency` | Что реально было потрачено. Неизменно. |
| `base_amount_minor`, `base_currency` | Пересчёт в базовую валюту бюджета. |
| `rate_num`, `rate_den` | Курс, применённый в момент записи. |
| `rate_date`, `rate_source` | Откуда и на какую дату взят курс. |

Изменение курса в справочнике **никогда** не трогает существующие операции.
Отчёт за март 2025 года будет одинаковым и сегодня, и через пять лет.

**Смена базовой валюты бюджета** — это не изменение настройки, а явная
администраторская операция: создаётся задача пересчёта, которая по историческим
курсам заполняет новые `base_amount_minor`/`base_currency`, и факт пересчёта
пишется в журнал событий. Владелец видит предупреждение до запуска.

### 3.4 Схема

```
users ──┬── user_settings
        ├── refresh_tokens
        └── budget_members ──── budgets ──┬── accounts
                                          ├── categories (self-ref parent_id)
                                          ├── transactions
                                          ├── budget_limits
                                          ├── goals
                                          ├── budget_invites
                                          └── events (журнал, seq)

currencies ──── exchange_rates
idempotency_keys
```

Полный DDL: `server/src/db/schema.sql` (SQLite) и `db/postgres/schema.sql` (Postgres + RLS).

Существенные детали:

- **Мягкое удаление** (`deleted_at`) на `transactions`, `accounts`, `categories`.
  Причина: жёсткий `DELETE` в мультидевайсной среде создаёт гонку «удалено на
  телефоне / редактируется на ПК», которую нечем разрешить — строки уже нет.
  С `deleted_at` конфликт «удалено vs изменено» разрешим и показывается пользователю.
- **`version INTEGER NOT NULL DEFAULT 1`** на каждой изменяемой сущности — основа
  оптимистичных блокировок.
- **Баланс счёта не хранится.** Он вычисляется: `initial_balance_minor + Σ операций`.
  Хранимый баланс — это денормализация, которая рассинхронизируется при первой же
  гонке. Путь масштабирования, если агрегат станет узким местом: материализованный
  снимок на конец месяца + дельта с начала месяца.
- **Переводы между счетами** — это одна строка `type='transfer'` с двумя сторонами
  (`account_id`/`amount_minor` и `counter_account_id`/`counter_amount_minor`),
  а не две связанные операции. Одна строка = одна транзакция = невозможно получить
  «половину перевода».

### 3.5 Валюта операции равна валюте счёта

Инвариант, который выглядит ограничением, но им не является:

```
transactions.currency = accounts.currency (для расходов и доходов)
```

Баланс счёта обязан быть однозначным числом в одной валюте. Если разрешить
записывать евро на рублёвую карту, «остаток на карте» перестаёт существовать
как величина. А в реальности при оплате евро рублёвой картой банк списывает
рубли — их и следует записывать.

Мультивалютность живёт на трёх других уровнях: валютные счета, базовая валюта
бюджета и валюта отображения. Для перевода между счетами в разных валютах
обе стороны задаются явно (`amount_minor` и `counter_amount_minor`) — курс
такого перевода определяет банк, а не наш справочник.

## 4. Realtime-архитектура

### 4.1 Журнал событий (transactional outbox)

Любая мутация записывает в одной транзакции две вещи: изменение сущности и строку
в `events`.

```
BEGIN
  UPDATE transactions SET amount_minor=?, version=version+1 WHERE id=? AND version=?
  INSERT INTO events (budget_id, entity, entity_id, op, actor_id, version, payload) VALUES (...)
COMMIT
-- только после COMMIT: broadcast подписчикам бюджета
```

`events.seq` — монотонно возрастающий счётчик (SQLite: `INTEGER PRIMARY KEY AUTOINCREMENT`,
Postgres: `BIGSERIAL`). Это даёт три свойства, которых нет у «просто WebSocket-broadcast»:

1. **Порядок.** Клиент применяет события строго по возрастанию `seq`.
2. **Гарантия доставки.** Событие уже в БД; если broadcast не дошёл — клиент
   догрузит его при переподключении.
3. **Отсутствие полной перезагрузки.** Переподключение = «дай всё, что после seq N».

### 4.2 Протокол WebSocket

```
client → { type: "auth", token: "<access JWT>" }
server → { type: "auth.ok", userId }

client → { type: "subscribe", budgetId, sinceSeq: 1428 }
         ← сервер проверяет членство в бюджете. Нет членства → { type:"error", code:"forbidden" }
server → { type: "subscribed", budgetId, seq: 1455, events: [...] }   // догрузка хвоста
   или → { type: "resync", budgetId, seq: 1455 }                      // разрыв слишком большой
server → { type: "event", seq: 1456, entity: "transaction", op: "update",
           actorId, actorClientId, actorName, payload: {...} }
```

**`sinceSeq` отсутствует и `sinceSeq: 0` — разные вещи.** Отсутствие означает
«у меня нет данных, возьму снимок»; ноль означает «данные есть, я стою в начале
журнала» — нормальное состояние только что созданного бюджета. Если их
перепутать, клиент нового бюджета молча не получит первые события.

- **Heartbeat:** ping каждые 25 с, разрыв при отсутствии pong 60 с.
- **Реконнект:** экспоненциальный backoff 1 с → 30 с с джиттером.
- **`resync`** отправляется, если `sinceSeq` отстал более чем на 500 событий или
  события уже подрезаны ретеншеном (90 дней). Клиент делает полный `GET /snapshot`.
- **Отзыв доступа:** при удалении участника сервер принудительно закрывает его
  подписки на бюджет — это не полагается на то, что клиент «сам отпишется».

### 4.3 Почему не polling и не SSE

- **Polling** — задержка/нагрузка выбираются друг против друга, и в мобильной сети
  это худший из вариантов по батарее.
- **SSE** был бы приемлем (однонаправленный поток server→client, а мутации через
  REST). Отклонён потому, что WebSocket уже нужен для двусторонней
  presence-функциональности («Анна сейчас добавляет операцию») и даёт
  один канал вместо двух. Плюс SSE плохо переживает HTTP/1.1-лимит соединений.

### 4.4 Масштабирование fan-out

MVP: один процесс, hub в памяти, `Map<budgetId, Set<connection>>`.

Прод (>1 инстанса): после `COMMIT` инстанс публикует `NOTIFY budget_events, '<budgetId>:<seq>'`;
все инстансы получают уведомление, читают события из `events` по `seq` и рассылают
своим подписчикам. Postgres остаётся источником истины — Redis не нужен, пока
частота событий не превысит ~1000/с.

## 5. Совместное редактирование и конфликты

### 5.1 Заявленный сценарий

> Телефон меняет операцию 1000 ₽ → 1500 ₽. Одновременно ПК меняет ту же операцию 1000 ₽ → 1200 ₽.

Что происходит по шагам:

```
Исходное состояние: { id: T1, amount: 100000, version: 7 }

t0  Телефон: оптимистично рисует 1500 ₽, шлёт PATCH /transactions/T1
             { amount_minor: 150000, version: 7, Idempotency-Key: <uuid-A> }
t0  ПК:      оптимистично рисует 1200 ₽, шлёт PATCH /transactions/T1
             { amount_minor: 120000, version: 7, Idempotency-Key: <uuid-B> }

t1  Сервер обрабатывает запрос телефона:
      UPDATE ... WHERE id=T1 AND version=7   → 1 строка
      version → 8, событие seq=1456 в журнал, broadcast

t2  Сервер обрабатывает запрос ПК:
      UPDATE ... WHERE id=T1 AND version=7   → 0 строк
      → HTTP 409 { code: "version_conflict",
                   current: { amount_minor: 150000, version: 8, updated_by: "Иван",
                              updated_at: "..." } }

t3  ПК получает 409. Сравнивает три состояния:
      base    = 100000  (то, что было при начале редактирования)
      mine    = 120000
      theirs  = 150000

    Поля пересекаются (оба изменили amount) → откатывает оптимистичное значение
    и показывает диалог:

      ┌────────────────────────────────────────┐
      │ Операцию изменил другой участник       │
      │                                        │
      │ Иван, только что:      1 500 ₽         │
      │ Ваше изменение:        1 200 ₽         │
      │                                        │
      │ [ Оставить 1 500 ₽ ]  [ Записать 1 200 ₽ ] │
      └────────────────────────────────────────┘
```

Ключевое: **изменение ПК не теряется молча и не перетирает чужое молча.**
Пользователь принимает решение осознанно.

### 5.2 Автоматическое разрешение непересекающихся правок

Диалог показывается только при реальном пересечении. Клиент отправляет **только
изменённые поля** (частичный PATCH) и хранит снимок `base`. При 409:

```
conflictingFields = keys(myPatch) ∩ keys(diff(base, theirs))

if (conflictingFields.isEmpty)
    → автоматический повтор PATCH с version = theirs.version   (тихое слияние)
else
    → диалог выбора
```

Практический пример: один участник поменял сумму, другой в это же время дописал
комментарий. Поля не пересекаются → оба изменения применяются, пользователь ничего
не видит. Это покрывает большинство реальных «конфликтов».

### 5.3 Почему не CRDT

CRDT (Yjs/Automerge) решает задачу слияния конкурентных правок без участия
пользователя. Для финансовых сумм это **антипаттерн**: у «1200 и 1500» нет
математически корректного слияния. LWW дал бы тихую потерю данных, а именно этого
требование запрещает. CRDT здесь оправдан только для одного поля — текстового
комментария, и ради него тащить рантайм CRDT нерационально.

Единственное место, где применён CRDT-подобный принцип — **удаление**:
`deleted_at` работает как tombstone, и «удалено» всегда выигрывает у «изменено»,
но пользователю показывается уведомление с возможностью восстановить.

### 5.4 Своё изменение и чужое: идентификатор устройства

Событие несёт не только `actorId` (кто), но и `actorClientId` (с какого
устройства). Это не избыточность.

«Телефон и компьютер одного человека» — заявленный основной сценарий продукта.
Если считать своим всё, что сделал текущий пользователь, то изменение с телефона
компьютер сочтёт собственным эхом и не станет пересчитывать производные данные —
балансы счетов и прогресс по лимитам, которые считаются на сервере. Внешне
операция появится, но итоги разъедутся.

Поэтому клиент генерирует `clientId` при открытии вкладки (`sessionStorage`),
передаёт его заголовком `X-Client-Id` при каждой мутации, а сервер сохраняет
его в событии. «Своё» = совпал `clientId`, а не `userId`.

### 5.5 Идемпотентность

Каждая мутация несёт клиентский `Idempotency-Key` (UUID v4, генерируется в момент
формирования намерения, а не в момент отправки).

```
POST /api/v1/budgets/:id/transactions
Idempotency-Key: 0f3c9a2e-...
```

Сервер:
1. `INSERT INTO idempotency_keys (key, user_id, request_hash) ...` — при конфликте
   ключа читает сохранённый ответ и возвращает его же (HTTP 200 + заголовок
   `Idempotency-Replayed: true`).
2. Если ключ тот же, а `request_hash` другой → `422 idempotency_key_reuse`.

Это делает безопасным повтор при обрыве сети: пользователь в метро нажал
«Сохранить», ответ не дошёл, клиент повторил — дубля не будет.

Ретеншен ключей — 24 часа.

### 5.6 Границы транзакций

Одна HTTP-мутация = одна транзакция БД. Внутри неё:
проверка прав → проверка ссылочной целостности в пределах бюджета → запись
сущности → запись события. Broadcast — **после** `COMMIT`, никогда внутри.

## 6. Система валют

### 6.1 Уровни валюты

```
Валюта операции      (transactions.currency)   — что реально потрачено
Валюта счёта         (accounts.currency)       — в чём ведётся счёт
Базовая валюта бюджета (budgets.base_currency) — в чём считается вся аналитика
Валюта отображения   (user_settings.display_currency) — личное предпочтение участника
```

Четыре уровня — не избыточность. Пример: семейный бюджет в RUB, у мужа
валютный счёт в USD, покупка сделана в EUR, жена хочет видеть всё в RUB.
Все четыре значения различны и все нужны.

Для русскоязычного пользователя при первом запуске: определяется `navigator.language`,
и если это `ru*`, базовая валюта = `RUB` без вопросов. Иначе — показывается выбор.

### 6.2 Справочник и курсы

`currencies` — код ISO 4217, название по-русски, символ, `exponent`, флаг активности.
Предзаполнено: RUB, USD, EUR, GBP, CNY, KZT, TRY, AED, JPY, CHF.
Добавление новой валюты = одна строка, без изменений кода.

`exchange_rates` — `(base, quote, valid_on, source)` → `rate_num/rate_den`.
Резолв курса для операции: последний курс с `valid_on <= occurred_on`.
Источник в MVP — ручной ввод + сид; в проде — ежедневная задача, тянущая ЦБ РФ
(для RUB-бюджетов) и ECB, с сохранением `source`.

Если курса на дату нет — операция создаётся, но `base_amount_minor = NULL` и
она помечается как «требует курса». Аналитика показывает такие операции отдельной
строкой, а не молча исключает и не подставляет случайный курс.

## 7. UX/UI и структура экранов

### 7.1 Принципы

- **Mobile-first, но не mobile-only.** Desktop — это не растянутый мобильный
  макет, а другая раскладка тех же данных: там, где на телефоне вертикальный
  стек и переходы между экранами, на десктопе — многоколоночная сетка и
  мастер-детали без навигации.
- **Одно доминирующее действие.** «Добавить расход» — самый заметный элемент
  интерфейса на всех разрешениях.
- **Никаких финансовых терминов.** «Остаток бюджета», а не «свободный денежный поток».

### Соглашения

- Все мутации требуют `Idempotency-Key`.
- Все `PATCH`/`DELETE` требуют `version` — иначе `428 Precondition Required`.
- Ошибка всегда: `{ error: { code, message, details? } }`, `code` — машиночитаемый.
- Коды: `400` валидация, `401` нет/просрочен токен, `403` нет прав в бюджете,
  `404` объект не существует **или** нет доступа (не различаем — защита от перебора),
  `409` `version_conflict`, `422` бизнес-правило, `429` rate limit.
- Пагинация — курсорная (`(occurred_on, id)`), не `OFFSET`.
- Суммы в JSON — **строки целых чисел**, не числа, чтобы исключить любой шанс
  попадания в float на любом клиенте.

## 9. Авторизация и права доступа

### 9.1 Аутентификация

- Пароль: **scrypt** (`N=2^15, r=8, p=1`), соль на пользователя, хеш в БД.
  Выбран вместо bcrypt/argon2, потому что доступен в стандартной библиотеке Node
  и не требует нативной сборки. Параметры вынесены в конфиг для будущего upgrade.
- **Access token** — JWT HS256, TTL 15 минут, в памяти клиента (не в localStorage).
- **Refresh token** — случайные 32 байта, в БД хранится только SHA-256 хеш,
  в браузере — `httpOnly; Secure; SameSite=Strict` cookie, TTL 30 дней.
- **Ротация с детекцией кражи:** каждый refresh выдаёт новый токен и помечает
  старый использованным. Повторное использование уже использованного токена
  = сигнал компрометации → отзывается вся «семья» токенов пользователя.
- Восстановление доступа: одноразовый токен на 30 минут, ответ на запрос
  восстановления **всегда** `204`, независимо от существования email.
- OAuth (Google/Yandex) — предусмотрен в модели (`user_identities`), в MVP не включён.
  Для русскоязычной аудитории первым имеет смысл добавить Яндекс ID.

### 9.2 Матрица прав

| Действие | Owner | Editor | Viewer |
|---|:---:|:---:|:---:|
| Просмотр операций, аналитики, счетов | ✅ | ✅ | ✅ |
| Создание/изменение/удаление операций | ✅ | ✅ | ❌ |
| Управление категориями, счетами, лимитами, целями | ✅ | ✅ | ❌ |
| Приглашение и удаление участников, смена ролей | ✅ | ❌ | ❌ |
| Изменение названия и базовой валюты бюджета | ✅ | ❌ | ❌ |
| Удаление бюджета | ✅ | ❌ | ❌ |

Владелец не может понизить/удалить сам себя, пока он единственный owner —
иначе бюджет остаётся без администратора.

### 9.3 Защита от подмены ID — три рубежа

Требование «пользователь не должен получить чужой бюджет, поменяв ID» решается
не одной проверкой, а инвариантом кода:

**Рубеж 1 — единая точка входа.** Любой маршрут вида `/budgets/:budgetId/*`
проходит через один preHandler:

```ts
const member = await requireMember(userId, budgetId, minRole)
// нет членства → 404 (не 403 — чтобы нельзя было перебором узнать,
// какие budgetId существуют)
```

Маршрут физически не может обратиться к данным, не пройдя его.

**Рубеж 2 — все запросы к данным скоупятся бюджетом.** В репозиториях нет метода
`getTransactionById(id)`. Есть только `getTransactionById(budgetId, id)`, и SQL
всегда содержит `WHERE budget_id = ?`. Подмена `id` на чужой даёт `404`,
а не чужие данные.

**Рубеж 3 — проверка ссылочной целостности при записи.** При создании операции
сервер проверяет, что `account_id` и `category_id` принадлежат **этому** бюджету.
Иначе участник бюджета A смог бы записать операцию на счёт из бюджета B.
Это самая часто пропускаемая дыра в подобных приложениях.

**Рубеж 4 (прод, Postgres) — RLS.** Политики на уровне БД.
Схема применена к PostgreSQL 16 и покрыта 26 тестами, которые намеренно
делают то, чего приложение делать не должно: читают таблицы целиком и
обращаются к строкам по чужому id. Подробности — §9.6.

Политики выглядят так:

```sql
ALTER TABLE transactions ENABLE ROW LEVEL SECURITY;
CREATE POLICY tx_member_read ON transactions FOR SELECT
  USING (budget_id IN (SELECT budget_id FROM budget_members
                       WHERE user_id = current_setting('app.user_id')::uuid));
CREATE POLICY tx_editor_write ON transactions FOR ALL
  USING (budget_id IN (SELECT budget_id FROM budget_members
                       WHERE user_id = current_setting('app.user_id')::uuid
                         AND role IN ('owner','editor')));
```

Соединение выполняет `SET LOCAL app.user_id = ...` в начале транзакции.
Даже ошибка в коде приложения (забытый `WHERE budget_id`) не приведёт к утечке.

### 9.6 Что показала проверка RLS на живом Postgres

Схема была написана «по учебнику» и выглядела правильной. Прогон на настоящем
PostgreSQL 16 вскрыл четыре дефекта, три из которых сделали бы приложение
неработоспособным, а один — тихо отключил бы всю защиту.

**1. Роль приложения не должна владеть таблицами.**
Владелец таблицы обходит RLS везде, где не включён `FORCE ROW LEVEL SECURITY`.
Если сервер подключается той же ролью, что выполняла миграции, второй рубеж
защиты исчезает молча — тесты на изоляцию при этом продолжают проходить,
потому что «проходят» они по совсем другой причине. Отсюда две роли:
`checkbudget_owner` для миграций и `checkbudget_app` для приложения,
обе `NOSUPERUSER NOBYPASSRLS`.

**2. `INSERT ... RETURNING` падает там, где `INSERT` проходит.**
Под RLS возвращаемая строка дополнительно прогоняется через SELECT-политику.
Политика чтения бюджета опиралась на членство, а создатель бюджета в момент
вставки участником ещё не является — строка в `budget_members` появляется
следующим оператором. Результат: создание бюджета падало с ошибкой
*записи* («new row violates row-level security policy»), хотя сам `INSERT`
политику проходил, а виновато было чтение.

Приложение использует `RETURNING` во всех путях создания, то есть на Postgres
оно бы просто не заработало. Исправление — политика чтения бюджета учитывает
и владельца: `USING (is_member(id) OR owner_id = app_user_id())`.

**3. `STABLE`-функция не видит строку, которую вставляет её же оператор.**
Тот же сценарий на `budget_members`: политика чтения вызывала `is_member()`,
объявленную `STABLE`, а такая функция работает со снимком на начало оператора
и вставляемой строки не видит. Добавление участника с `RETURNING` падало.
Исправление — человек всегда видит собственное членство:
`USING (user_id = app_user_id() OR is_budget_owner(budget_id) OR is_member(budget_id))`.

**4. `FORCE RLS` распространяется и на миграции.**
Сид, выполняемый владельцем схемы, отвергался политиками, потому что
`app.user_id` не был установлен. Это правильное поведение, но о нём нужно
знать: любой сид или backfill обязан объявить, от чьего имени пишет.

Отдельно — ловушка, которую удалось обойти по построению: если включить
`FORCE` на `budget_members`, политика этой таблицы начнёт вызывать
`is_member()`, который читает `budget_members`, и Postgres оборвёт это
ошибкой *infinite recursion detected in policy*. Поэтому `budgets` и
`budget_members` работают с `ENABLE`, но без `FORCE`: их читают
`SECURITY DEFINER`-функции проверки прав, и владелец схемы обязан
иметь к ним прямой доступ.

Вывод, который стоит держать в голове: **RLS нельзя считать написанным,
пока он не выполнен.** Политики компилируются молча, а ошибки в них
проявляются либо как отказ в работе, либо — гораздо хуже — как
незаметно отключённая защита.

### 9.4 Безопасность realtime-подписок

Отдельный и часто забываемый вектор: WebSocket проверяется только при коннекте,
а подписки живут часами.

- `subscribe` валидирует членство **на момент подписки**, а не на момент коннекта.
- При изменении/удалении членства сервер рассылает служебное событие и
  **принудительно закрывает** подписки затронутого пользователя.
- Access-токен в WS проверяется на срок жизни; при истечении сервер шлёт
  `{type:"reauth"}`, клиент обновляет токен и переотправляет `auth`.
- Событие содержит только данные того бюджета, на который есть подписка —
  hub индексирован по `budgetId`, «широковещательных» рассылок нет.

### 9.5 Прочее

- Rate limit: `10/мин` на `/auth/login` по IP+email, `300/мин` на остальное по userId.
- CORS — белый список источников, `credentials: true`.
- Все входные данные проходят Zod-схему; неизвестные поля отбрасываются.
- Заголовки: HSTS, `X-Content-Type-Options`, CSP без `unsafe-inline`.
- Логи не содержат сумм, email и токенов.

## 10. Offline и плохое соединение

### 10.1 Три уровня деградации

| Состояние | Поведение |
|---|---|
| Онлайн | Оптимистичный UI + подтверждение сервером + realtime |
| Плохая сеть | Оптимистичный UI, очередь с ретраями, индикатор «отправляется» |
| Офлайн | Полностью рабочее приложение на локальном кеше, очередь мутаций |

### 10.2 Механика

**Чтение.** Service Worker кеширует оболочку приложения (app shell).
Данные бюджета лежат в IndexedDB как нормализованный снимок + `lastSeq`.
Запуск: рендер из IndexedDB немедленно → параллельно `GET /snapshot?since=lastSeq`
→ применение дельты. Приложение открывается мгновенно и работает без сети.

**Запись.** Мутация проходит четыре шага:

```
1. Применить локально (оптимистично) + пометить pending
2. Записать в очередь IndexedDB: { idempotencyKey, method, url, body, baseSnapshot }
3. Попытаться отправить
4. Успех → снять pending, применить ответ сервера
   409  → разрешение конфликта (§5)
   Сеть → оставить в очереди, ретрай
```

Очередь **строго последовательная в пределах сущности** — иначе «создать
операцию» и «изменить её же» могут прийти в обратном порядке. Между разными
сущностями параллелизм допустим.

Ретраи: экспоненциальный backoff с джиттером, максимум 6 попыток, затем операция
переходит в состояние «не отправлено» и показывается пользователю с кнопкой
«Повторить». Молчаливого отбрасывания нет.

`navigator.onLine` используется только как подсказка — реальным признаком
считается результат запроса, потому что `onLine === true` в Wi-Fi без интернета.

### 10.3 Три различия, без которых офлайн не работает

Каждое выглядит мелочью и каждое ломает офлайн-режим целиком.

**1. «Сервер отверг» ≠ «сервер недоступен».**
Ответ мог прийти не от приложения, а от прокси или балансировщика: `502`,
`503`, `504`, а на дев-прокси — и `500`. Такие ответы не несут наш конверт
`{ error: { code } }` и означают «повтори позже», а не «запрос отвергнут».
Если их спутать, очередь мутаций будет молча вычищаться при каждом рестарте
бэкенда — то есть офлайн-режим перестанет существовать именно тогда, когда он нужен.

Правило: `408/502/503/504`, а также любой `5xx` без нашего кода ошибки —
это недоступность, мутация остаётся в очереди.

**2. «Сессии нет» ≠ «не удалось спросить про сессию».**
Холодный старт начинается с `POST /auth/refresh`. Если считать любую его
неудачу отсутствием сессии, приложение будет выбрасывать на экран входа при
каждом выходе из метро — с полным локальным кешем на руках.

Только `401` и `403` означают «нужен вход». Всё остальное — офлайн-старт:
приложение поднимается из снимка в IndexedDB и продолжает попытки в фоне.
Для этого рядом с кешем хранится подсказка о последней сессии (кто вошёл,
какой бюджет открыт) — без токенов, только то, что нужно нарисовать интерфейс.

**3. Отправка из очереди должна сшивать оптимистичную запись с ответом.**
Мутация уходит на сервер двумя путями: сразу или позже, из очереди. Во втором
случае вызывающего кода уже нет — он завершился ошибкой сети. Если сшивание
делать только в первом пути, операция навсегда останется серой «отправляется»
и задвоится, когда её же принесёт realtime-событие с настоящим `id`.

Поэтому подстановка ответа сервера вместо локальной записи выполняется в одном
месте — на выходе доставки, общем для обоих путей.

### 10.4 Гарантии

- **At-least-once доставка + идемпотентность = ровно один эффект.**
- Мутации не теряются при закрытии вкладки — они уже в IndexedDB.
- При долгом офлайне (> ретеншена событий) клиент получает `resync` и делает
  полную перезагрузку — но **сначала** отправляет свою очередь.

## 11. Потенциальные проблемы и решения

| Риск | Последствие | Решение |
|---|---|---|
| Округление при конвертации | Расхождение в отчётах на копейки | Целочисленная арифметика в BigInt, округление ровно один раз, half-up. Суммы в JSON — строки. |
| Изменение курса задним числом | «Поехавшая» история | Курс замораживается в строке операции. Пересчёт — только явная администраторская операция. |
| Тихая потеря правки | Потеря доверия | `version` + 409 + диалог. Автослияние только при непересекающихся полях. |
| Дубли при обрыве сети | Двойной расход | `Idempotency-Key` на каждой мутации. |
| Гонка «удалено vs изменено» | Ошибка «объект не найден» | Мягкое удаление, tombstone выигрывает, пользователю показывается уведомление. |
| Отставший клиент после офлайна | Рассинхронизация | `seq` + `replay`, при большом разрыве — `resync`. |
| Отзыв доступа не применён к WS | Утечка данных после исключения из бюджета | Принудительное закрытие подписок при изменении членства. |
| Перебор `budget_id` | Утечка | 404 вместо 403 + скоуп по `budget_id` во всех запросах + RLS. |
| Медленная аналитика на больших объёмах | Тормозящий дашборд | Индексы `(budget_id, occurred_on)`, `(budget_id, category_id, occurred_on)`. Далее — материализованные месячные агрегаты. |
| Рост таблицы `events` | Раздувание БД | Ретеншен 90 дней + партиционирование по месяцам в Postgres. |
| Часовые пояса | Операция «уехала» на день | `occurred_on` — календарная дата (`DATE`), а не timestamp. Отдельно `created_at` в UTC. |
| Смена базовой валюты бюджета | Несопоставимая аналитика | `base_currency` хранится в строке операции. Смена = явная задача пересчёта с предупреждением. |
| Хранимый баланс счёта | Рассинхронизация при гонке | Баланс вычисляется. Денормализация — только когда станет узким местом. |
| Утечка refresh-токена | Захват аккаунта | Ротация + детекция повторного использования + отзыв всей семьи токенов. |
| Путь к БД зависит от cwd | Приложение работает, но с пустой базой: `npm run` и `node dist/` стартуют из разных каталогов | Относительный путь разрешается от корня пакета, найденного по `package.json`, а не от `process.cwd()`. |
| Изменение схемы на живой базе | `CREATE TABLE IF NOT EXISTS` не меняет существующие таблицы | Версионированные миграции по `PRAGMA user_version`; шаги только добавляются и никогда не редактируются задним числом. |
| Событие от своего же второго устройства | Производные данные (балансы, лимиты) не пересчитываются | Событие несёт `actorClientId`; «своё» определяется устройством, а не пользователем (§5.4). |
